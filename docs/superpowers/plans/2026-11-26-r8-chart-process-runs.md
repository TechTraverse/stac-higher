# R-8 · Chart: the process-runs plane (runs namespace, RBAC, NetworkPolicies, Kueue and NodePool objects, registry mirror map) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or superpowers:subagent-driven-development) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Tracking:** #144 (epic #136).

**Goal:** When the `stac-higher` chart is installed, everything the Kubernetes executor (K-5) needs to start a run exists: the runs namespace with Pod Security `restricted`, the token-less run ServiceAccount, the pipeline's Role and RoleBinding, the default-deny NetworkPolicy the executor checks plus exactly two egress allow policies, the Kueue objects (LocalQueue, priority classes, admission policy, ResourceFlavors, ClusterQueue), and the EKS Auto Mode NodeClass and NodePools for runs. Flavors, quotas, NodePools and the hardware-profile document's `backend.kubernetes` blocks all come from **one** values block, so a profile cannot name a flavor that does not exist and the Kueue quota cannot exceed what the NodePool can provision.

**Architecture:** New templates under `infra/helm/stac-higher/templates/` (`runs-namespace.yaml`, `runs-rbac.yaml`, `runs-networkpolicies.yaml`, `runs-kueue.yaml`, `runs-cluster-kueue.yaml`, `runs-nodes.yaml`) and helpers in a new `templates/_runs.tpl`. Objects in the runs namespace render unconditionally (the chart already sets `PROCESS_EXECUTOR=kubernetes`); cluster-scoped objects render behind `processRuns.clusterObjects` (spec §13 Q1), NodeClass and NodePools additionally behind `processRuns.nodes.enabled`. The hardware-profile helper derives each profile's `backend.kubernetes` from `processRuns.families`. Files the chart cannot read (`infra/kubernetes/`, `infra/kueue/`) are reproduced as templates and pinned by drift tests that read those files. One new cross-runtime contract fixture pins the names and labels the executor and the chart must agree on. The only pipeline change is a test reading that fixture.

**Tech Stack:** Helm 3.22 / 4.3, chart `apiVersion: v2`; vitest render suites over `helm template` (R-6 harness `infra/helm/stac-higher/tests/render.mjs`); kubeconform 0.8.0 with Kueue v0.20.8 schemas generated by K-6's `scripts/check-kueue.sh`; trivy config; pytest for the fixture. No new npm or Python dependency.

**Spec:** `docs/superpowers/specs/2026-11-02-deployment-artifacts-design.md` §4.1, §5 (amended: mirrors rewrite platform images only), §6.1, §6.2, §6.3, §6.5, §10, §13 Q1; `docs/superpowers/specs/2026-09-02-process-compute-k8s-kueue-design.md` §3.4, §6.2, §6.3, §7, §8, §11.1; ADR 0019, ADR 0024, ADR 0013. ## Rulings

Each: the decision — why — the cost if it is wrong.

- **R8-R1 · The chart creates the runs namespace; everything in it has a fixed name.** `processRuns.createNamespace: true` (default) renders Namespace `processRuns.namespace` with exactly K-5's two Pod Security labels (plus the chart's standard labels); `false` renders no Namespace and the README says the cluster team must create it with those labels. The namespace must differ from the release namespace (render fails otherwise): K-5's rule "the namespace holds nothing else" (I-184) cannot hold if the app and pipeline live there. No `helm.sh/resource-policy: keep`: uninstall deletes the namespace and with it every run Job and run Secret (live run credentials), which is the cleanup we want. *Why:* the executor refuses to run without the namespace's objects, and Helm can only put objects into a namespace that exists at apply time. *Cost:* `helm uninstall` with runs in flight kills them (the README says to drain first, I-182's rule); one release per cluster.
- **R8-R2 · RBAC is K-5's four objects, reproduced, with a drift test.** Namespace, ServiceAccount `stac-higher-run` (no annotations at all, so no IRSA role ARN can be added by values; no token), Role `stac-higher-pipeline` (K-5's six rules verbatim), RoleBinding with subject `identity.serviceAccounts.pipeline` in `identity.namespace`. The drift test loads `infra/kubernetes/*.yaml`, renders the chart with default names, strips the chart's own metadata (`helm.sh/*`, `app.kubernetes.io/*` labels) and requires deep equality object for object. *Why:* Helm cannot read outside the chart (K5-R23 precedent); K-5's unit tests enforce the Role file, so equality transfers that proof to the chart. *Cost:* two copies; the test fails on any edit to one side only, which is the point.
- **R8-R3 · Runs NetworkPolicies: K-5's exact default-deny plus two egress-only allows, IPv4, DNS by explicit peer.**
  - `stac-higher-runs-default-deny`: exactly the shape in `infra/kubernetes/README.md` (`podSelector: {}`, `policyTypes: [Ingress, Egress]`, no rules).
  - `stac-higher-runs-process-isolated`: `podSelector.matchLabels` exactly `{stac-higher.run-kind: process, stac-higher.network-level: isolated}`, `policyTypes: [Egress]`, egress = (DNS peers, UDP+TCP 53) and (object-store peers, `processRuns.network.objectStorePorts`, default TCP 443).
  - `stac-higher-runs-image-scan`: `{stac-higher.run-kind: image_scan, stac-higher.network-level: scanner}`, `[Egress]`, the same two rules plus TCP 443 to `0.0.0.0/0` with `except: [169.254.0.0/16, …processRuns.network.scannerEgressExcept]`.
  - **DNS peers are required** (`processRuns.network.dns`, render fails when empty). EKS Auto Mode runs CoreDNS on each node and has no `kube-dns` Service, so the peer there is `ipBlock: {cidr: <service CIDR .10>/32}`; on a cluster with a `kube-dns` Service it is a namespace + pod selector. A default that is wrong on the target platform would resolve nothing and fail every run silently, so there is none. Every `ipBlock` among the DNS peers must be a `/32` (or `/128`): port 53 to a wide range is an exfiltration channel to any resolver.
  - **Object store peers** = `ipBlock`s from `aws.s3PrefixListCidrs` (Terraform's S3 managed prefix list, spec §6.5) plus `processRuns.network.objectStore` (peers, e.g. an in-cluster MinIO's selectors); the union must be non-empty.
  - **IMDS and the Pod Identity agent.** NetworkPolicy can only allow, so the "explicit block" is: no allow may cover link-local. The render refuses an object-store `ipBlock` whose prefix is shorter than `/8` or whose first octet is `169`; the scanner's `0.0.0.0/0` carries `except: 169.254.0.0/16` (IMDS `169.254.169.254` and the Pod Identity agent `169.254.170.23`); a render test does real CIDR math over every runs policy. The node side is Auto Mode's fixed IMDSv2 hop limit 1 (facts table), and the custom NodeClass's `networkPolicy: DefaultDeny` (R8-R8).
  - **No other policy may select run pods**: a render test pins that the runs namespace holds exactly these three NetworkPolicies, the two allows select on both labels with `matchLabels` only (no `matchExpressions`), and no runs policy has an `ingress` rule.
  *Why:* this is the K-5 label contract and the spec's §6.5 shape, with the platform facts the spec did not have. *Cost:* the scanner can reach any address on 443 except link-local, including the cluster API endpoint and in-VPC services on 443 (it has no token; a deployment adds its VPC CIDR to `scannerEgressExcept` when its registries are public); IPv6 clusters are not isolated (IPv4 egress is unfiltered there, facts table) and are unsupported for runs (ISSUES).
- **R8-R4 · Kueue and Karpenter are cluster prerequisites, signalled by values, not by `.Capabilities`.** No `.Capabilities.APIVersions` gate: `helm lint` cannot be given API versions, so a gate would make every lint scenario fail or force lint to run with the plane off. Instead the namespaced Kueue object (LocalQueue) always renders, the cluster-scoped Kueue objects and the admission policy render with `processRuns.clusterObjects`, NodeClass and NodePools additionally with `processRuns.nodes.enabled`. A cluster without the CRDs fails `helm install` before Helm creates anything ("resource mapping not found … ensure CRDs are installed first"; Helm builds every manifest against discovery first), and Argo CD/Flux fail the sync the same way. *Cost:* the operator sees Helm's generic message instead of ours; the README prerequisites name the CRDs; R-11 confirms the pre-create refusal.
- **R8-R5 · One source of truth: `processRuns.families`.** A *family* is one ResourceFlavor, one ClusterQueue flavor entry with its quota, one NodePool, and the `backend.kubernetes` block of every profile mapped to it:
  ```yaml
  processRuns:
    defaultFamily: cpu-default     # profiles with gpu_count null and no entry in profileFamilies
    profileFamilies: {}            # profile id -> family (required for every GPU profile)
    families:
      cpu-default:
        enabled: true
        dedicatedNodes: true       # node label stac-higher.io/flavor=<name> + taint stac-higher.io/runs=true:NoSchedule
        extraTaints: []            # e.g. [{key: nvidia.com/gpu, effect: NoSchedule}]
        gpuResource: ""            # e.g. nvidia.com/gpu; "" = a CPU family
        runtimeClass: ""           # "" -> runtime_class null
        quota: {cpu: 16, memoryGi: 64, gpus: 0}       # Kueue nominalQuota
        nodePool:
          requirements: [...]      # Karpenter requirements (EKS Auto Mode labels)
          headroom: {cpu: 4, memoryGi: 16}            # NodePool limits = quota + headroom (R8-R7)
  ```
  The profile document's `backend.kubernetes` is **derived**: `queue: process-runs`; `node_selector: {stac-higher.io/flavor: <family>}` when `dedicatedNodes`, else `{}`; `tolerations`: the runs taint as `{key, operator: Equal, value: "true", effect: NoSchedule}` when `dedicatedNodes`, then each `extraTaints` entry (`operator: Exists` when it has no value); `runtime_class`; `extended_resources: {<gpuResource>: gpu_count}` for a GPU family, else `{}`. A document that already carries `backend.kubernetes` must equal the derived block (compared as `toJson`) or the render fails naming the profile, so a copied `kind.json`-style document still works and nothing is silently overwritten. Render-time checks: every profile resolves to an enabled family; a GPU profile maps to a GPU family and a CPU profile never does; each profile's `cpu.max` ≤ `quota.cpu`, `memory_mb.max` ≤ `quota.memoryGi × 1024`, `gpu_count.max` ≤ `quota.gpus` (K6-R11: a profile whose maximum exceeds the quota pends forever); the image policy's `scan_limits.memory_mb` and the scan's 1 CPU fit the default family; with more than one enabled family every family has `dedicatedNodes` (distinct labels make flavor assignment unambiguous); `profileFamilies` keys name profiles in the document. *Why:* spec §4.1 and §7.3 require flavors, quotas, NodePools and the profile file to change together; deriving makes inconsistency unrepresentable rather than merely tested. Families are a map (overridable per key with `--set`) with an `enabled` flag, because removing a map entry needs a `null` override (Global Constraints). *Cost:* the chart owns the profile document's `backend.kubernetes`; a deployment that wants a shape the families cannot express (per-group queues, I-96) needs a chart change.
- **R8-R6 · The runs taint is tolerated by the flavor; a GPU taint is required by it.** Every dedicated family's ResourceFlavor carries `nodeLabels: {stac-higher.io/flavor: <name>}` and `tolerations: [the runs toleration]` (Kueue injects both on admission), and `nodeTaints:` only the family's `extraTaints`. *Why:* image scans carry no profile (facts table, K5-8), so their pods have no selector and no toleration; with the runs taint as a flavor `nodeTaint` a scan would be inadmissible forever and `images-seed` would fail. With the toleration on the flavor, Kueue places scans on the first CPU flavor with room (the default family is listed first) and injects what they need; with `extraTaints` as `nodeTaints`, a workload without the GPU toleration (every scan, every CPU profile) can never be assigned a GPU flavor. Profiles still carry the full selector and tolerations, so a pod is right even before injection. *Cost:* relies on Kueue's admission-time injection (documented behaviour, R-11 checks it with a scan); the named fallback is a pipeline change giving profile-less specs the default profile's block.
- **R8-R7 · NodePool limits = Kueue quota + headroom, not equal.** Spec §7.3 says quota "must equal" the NodePool limits so that Kueue never admits what Karpenter will not provision. Karpenter's limits count the capacity of the nodes it launches, which includes kubelet/system reservations and daemon pods, while Kueue counts pod requests; equality would admit runs whose last pod cannot fit and sits `Pending` until `waitForPodsReady` evicts it. So `limits.cpu = quota.cpu + headroom.cpu`, `limits.memory = (quota.memoryGi + headroom.memoryGi)Gi`, `limits[<gpuResource>] = quota.gpus` (a GPU is not reserved by the system). Both come from the same family entry, so they still change together. Values are integers (`cpu` cores, `memoryGi`, `gpus`) so the arithmetic is plain Helm `add`. *Cost:* a wrong headroom leaves capacity idle (too large) or brings back the Pending tail (too small); R-11 measures by filling the quota. Spec §7.3 gets a one-line amendment.
- **R8-R8 · Node templates are EKS Auto Mode only; the chart renders its own NodeClass by default.** `processRuns.nodes.enabled: true` renders, per enabled family, a `karpenter.sh/v1` NodePool `stac-higher-runs-<family>` (template label `stac-higher.io/flavor`, taints, requirements, `nodeClassRef` to the NodeClass) and, with `nodes.nodeClass.create: true`, one `eks.amazonaws.com/v1` NodeClass `stac-higher-runs` with `role`, `subnetSelectorTerms`, `securityGroupSelectorTerms` (all required, render fails naming them), `networkPolicy: DefaultDeny`, `networkPolicyEventLogs`, `advancedCompute.kubelet.podPidsLimit` (default 4096; I-180), optional `ephemeralStorage` and `tags`. `create: false` points the NodePools at `nodeClass.name` (e.g. Auto Mode's `default`), and the README says that NodeClass then owns `podPidsLimit`. `DefaultDeny` makes a runs node deny any pod no policy selects, so deleting the runs namespace's policies (I-183) fails closed on those nodes too. *Why:* `podPidsLimit` exists only on a custom NodeClass; IMDS hop limit 1 is fixed by Auto Mode, so the chart needs no field for it. Self-managed Karpenter (EC2NodeClass, `karpenter.k8s.aws/*` labels, AL2023 `spec.kubelet.podPidsLimit`, `metadataOptions` hop limit 1 by default) is documented as an example in the README with `nodes.enabled: false`, not templated: the first environment is Auto Mode (spec §4.1) and a second template set doubles the render matrix for no deployment. *Cost:* the human must supply the node role (with an EKS access entry), subnet and security-group selectors from the cluster repo; non-Auto-Mode clusters copy the README example.
- **R8-R9 · NodePools belong in this chart, behind the toggles.** The epic, the spec (§4.1, §6.1 "cluster objects" row) and #144 say the chart ships the runs NodePool behind `processRuns.clusterObjects`, because NodePool limits, Kueue quota and the profile file must change together (R8-R5); Q1 (who owns cluster-scoped objects) stays open, and the toggle is the answer for a cluster team that says no: `clusterObjects: false` (or only `nodes.enabled: false`) and they apply `helm template … --set processRuns.clusterObjects=true` output as their reference. GPU families use the same template; the first environment enables none, and K-8 (#16) proves them live. *Cost:* the release needs RBAC for cluster-scoped kinds (ClusterQueue, ResourceFlavor, WorkloadPriorityClass, ValidatingAdmissionPolicy(+Binding), NodePool, NodeClass); the README and `docs/releases.md` say so.

Schema: every map above closed except `profileFamilies` and `families` (`additionalProperties` = the family schema, itself closed; family names match `^[a-z0-9]([-a-z0-9]{0,44}[a-z0-9])?$` so `stac-higher-runs-<name>` fits 63), `quota.*` and `headroom.*` integers ≥ 0 (`quota.cpu`, `quota.memoryGi` ≥ 1), `podPidsLimit` `anyOf [{const: -1}, {minimum: 100}]`, `networkPolicy`/`networkPolicyEventLogs` enums, `objectStorePorts` items 1–65535, `extraTaints[].effect` ∈ {NoSchedule, NoExecute}. The schema cannot express "required when"; `stac-higher.validateRuns` does, naming the key. Family keys are not `required` in the schema: the templates default each absent key to the `cpu-default` entry's shape (`enabled: true`, `dedicatedNodes: true`, `extraTaints: []`, `gpuResource: ""`, `runtimeClass: ""`, `headroom: {cpu: 0, memoryGi: 0}`), so a deployment adding a family writes only what differs; `quota` and `nodePool.requirements` have no default for a new family and are refused when missing (with `nodes.enabled`, for the requirements).
